# Forge Angular Adapter

Typed Angular components, directives, and services wrapping `@tylertech/forge` custom elements.

## Purpose

Angular's `CUSTOM_ELEMENTS_SCHEMA` lets templates reference `forge-*` tags directly, but loses type-checking on
inputs/outputs and requires manually registering each custom element. This package wraps every Forge custom
element in a typed `NgModule`-declared `Component` proxy that sets values via the JS property API and registers
the element's `define<X>Component()` function automatically.

`@tylertech/forge` is a **peerDependency**, not bundled — consumers install it alongside this package.

## Architecture

- `src/lib/<component>/` — one folder per Forge component (`~97` total), each with a generated
  `<component>.component.ts` (the proxy) and `<component>.module.ts` (declares/exports it, calls
  `define<X>Component()`). **These are generated by `pnpm run --filter @tylertech/forge-angular generate-proxies`
  from `@tylertech/forge`'s `custom-elements.json` manifest (config: `generate-proxies.json`) — do not hand-edit
  them, regenerate instead.** Several components also ship `*-value-accessor.directive.ts` (Angular Forms
  `ControlValueAccessor` implementations).
- `src/lib/core/` — hand-written, not generated. `dynamic-component/dynamic-component.service.ts` creates and
  attaches Angular components dynamically (used by the overlay services below).
- `src/lib/{dialog,toast,popover,bottom-sheet}/` — hand-written overlay services (`*.service.ts`) plus their
  `*-config.ts`/`*-ref.ts`/`*-injector.ts` support types, for imperatively opening a Forge overlay with an
  Angular component inside it.
- `src/public-api.ts` — barrel export, the `ng-packagr` entry file.
- `src/dev/` — internal Angular CLI demo application exercising the library's components against the
  workspace's `@tylertech/forge` build. Not published (excluded from `tsconfig.build.json`).
- `schematics/` — `ng-update` migration schematics, built separately via plain `tsc` and shipped as a `dist/`
  asset (see `ng-package.json`'s `assets`).

## Publishing note

This package builds via `ng-packagr` (Angular Package Format), which generates its own `package.json` inside
`dist/`. That generated manifest is never read at publish time — `changeset publish` always publishes from this
directory using the hand-authored `package.json` at the package root, whose `main`/`module`/`exports` fields are
manually kept in sync with ng-packagr's deterministic output paths (`dist/fesm2022/tylertech-forge-angular.mjs`,
`dist/index.d.ts`). If you ever change the entry file name or ng-packagr version, re-verify those paths with
`pnpm pack --dry-run` before assuming they still match.

## Commands

```bash
pnpm run --filter @tylertech/forge-angular build   # ng-packagr build to dist/
pnpm run --filter @tylertech/forge-angular test     # Vitest via @angular/build:unit-test
pnpm dev:forge-angular                              # demo app dev server
```

## Testing

Uses Angular's `@angular/build:unit-test` builder with `runner: "vitest"` (still marked experimental by the
Angular team as of Angular 20/21), running in real Chromium via the builder's own `browsers` option (configured
in `angular.json`, not `vitest.config.ts` — the builder owns test execution and does not support arbitrary
Vitest config). Real-browser mode is required here: jsdom's `ElementInternals`/`showModal`/`matchMedia` gaps
break Forge's custom elements (ARIA reflection, native dialogs, reduced-motion detection).

Prefer smoke tests over exhaustively testing every generated component wrapper: one test validates the generated
proxy pattern itself (e.g. `button.component.spec.ts`), and the hand-written pieces (`DynamicComponentService`,
the overlay services) get real coverage since they have the actual logic.
